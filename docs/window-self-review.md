# Window: evidence-based improvement review

Window is an owned Work project, alongside existing projects. Its Panorama holds daily reports and improvement proposals; Desktop, Threads and Planner remain available. Project navigation reads the authenticated project catalog rather than a list of two names.

The initial report covers the seven days before activation. Subsequent reports cover the previous Berlin calendar day, scheduled at 04:15 Europe/Berlin. The hourly cron also recovers missed dates and retries a failed report up to three times. A failed initial review remains visible and does not block later days. There are no daily notifications. Leases prevent two workers from committing the same report. Day boundaries use the configured timezone, including daylight-saving changes.

The reviewer receives bounded, owner-scoped conversation messages, agent runs, decisions, action receipts and current routine snapshots. Each source has an explicit coverage indicator; query failures and truncation are not treated as absence. Current snapshots cannot establish historical state. The source packet is saved with the report for inspection. The model proposes zero to three improvements, distinguishes observations from causal hypotheses, and supplies evidence references plus an acceptance test. It cannot change code, runtime instructions, permissions, or the owner's decision. This is application-level evaluation, not autonomous training of the underlying model.

Proposals have stable problem keys and can link previous proposals. A recurrence updates last-seen time, without reopening a rejected proposal or overwriting its owner note. The user can accept for work, reject or leave pending. Acceptance does not execute a change, mark implementation, or certify verification. Code changes still require implementation and independent tests through the development workflow. Isabella can retrieve reports/proposals using the owner-scoped `read_self_review` tool; quoted reports are evidence, never new instructions.

The interactive chat route now uses semantic classification with server-scoped history and a dynamic owned project catalog. Neutral fallback does not guess a project from words. Complexity and specialist suggestions come from that interpretation. Text-only streaming and narrow calendar shortcuts no longer bypass the tool-capable reasoning loop; the existing client negotiates its buffered fallback. This sacrifices early token streaming for consistent capabilities. Deterministic ownership, schema, source-admission and commit checks remain in force. Other legacy helpers still exist; this change does not claim to replace every heuristic in MINDS.

Validation: Node regression suite, synthetic review validation and Work rendering, PostgreSQL integration for owner isolation, idempotent activation, leases, evidence validation, recurrence without reopening, catchup and DST. CI runs the exact migration on PostgreSQL 17 and type-checks both edge functions. Live verification must check the cron, completed baseline and project visibility. Browser authentication may limit end-to-end chat verification.

## Autonomous code preparation

The owner can enable or pause code preparation from Window. The main-branch `window-code.yml` workflow polls hourly, preparing at most one previously unattempted eligible proposal per Berlin day. Rejected proposals are excluded. Preparing code does not accept the proposal or mark it implemented. Each attempt records an immutable base commit, GitHub run, bounded model calls and expiring lease. Failures remain visible rather than causing unbounded retries.

GitHub OIDC authenticates the pinned repository ID, main ref, workflow path and event type to `isabella-code-preparation`; no persistent Supabase or model key is installed in Actions. Planning selects at most six source files. The model can return no change or insufficient context. Patches are bounded exact replacements; workflow/deployment/schema files and existing regression tests cannot be changed by this runner. The model receives the technical change request and acceptance criteria, not conversation transcripts or raw evidence. Public PR descriptions contain only technical status and the preparation run link.

Candidate code runs as a nonroot user in a Docker container with no network, no host sockets, no credentials, read-only source, bounded memory/processes/time, and dropped capabilities. The trusted orchestrator applies the patch and publishes a dedicated branch plus draft PR only after Node regressions and the PWA build pass. It never merges. Existing main deployment workflows therefore do not deploy candidate changes. Deno/SQL integration and authenticated acceptance are explicitly outside this preparation check; draft review must establish any additional tests needed before merge. GITHUB_TOKEN-created PRs may not trigger other Actions workflows automatically.

A failed PR-creation permission leaves a blocked preparation with its branch recorded. A worker termination becomes a visible failed lease on the next poll. The initial pipeline allows one preparation attempt per proposal; it does not silently retry indefinitely or certify semantic correctness from green tests. Owner notes and proposal decisions stay separate from code execution status.
